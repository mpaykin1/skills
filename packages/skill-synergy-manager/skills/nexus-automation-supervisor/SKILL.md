# Skill Nexus — Automation Supervisor (обязательный дочерний скилл)

## Главная задача

При **каждом** вызове Skill Nexus, в дополнение к полному живому реестру всех авторских скилов, проверяй ВСЕ включённые автозадачи пользователя и улучшай их *фактическую* продуктивность. Не требуй от владельца вручную запускать модули. Этот скилл предназначен для самого запланированного запуска `Скилы-5 — Skill Nexus` (:48 Asia/Tbilisi) и **не должен** самостоятельно создавать шестую задачу или менять время остальных.

## Обязательный цикл одного запуска

1. **Точный реестр:** `skills__list` и все страницы `mcp__Plugin_Creator__list_owned_personal_plugins`, затем `https://raw.githubusercontent.com/mpaykin1/skills/main/catalog.json`. Список неполон — запрети массовое удаление/замену и не заявляй синхронизацию. Сравни версии и реальные доступные инструменты; найди новые скилы.
2. **Факты по задачам:** `mcp__Automations__peek({})` для полного перечня. Для **каждой включённой задачи** отдельно вызови `peek({jawbone_id})`, чтобы получить `run_details.last_run` и `latest_result`, при необходимости `get` для сохранённых инструкций. Просматривай последние GitHub PR/commits/Actions настоящей ветки; не выводи успешный кодовый запуск из текста задачи или ссылки на неподтверждённый PR. Если доступен только последний запуск — пометь историю как неполную. Запрещено автоматически открывать личные данные из unrelated задач и публиковать сырые логи.
3. **Карта навыков:** для каждой задачи вычисли `назначенный скилл → реально вызванные модули и инструменты → артефакт → PR/commit SHA → реальная проверка`. Назначенный и фактически применённый — разные факты. Фраза в prompt «читай SKILL.md» не доказывает вызова скила. Утверждай использование лишь по настоящему подтверждению в доступной трассе, коммите или артефакте; если данных недостаточно — `unverified`.
4. **Узкие места:** ищи `failed`, `requires_user_action`, `in_progress` без прогресса, `no_update`, повторные нулевые результаты, хроническую блокировку, отсутствующие/устаревшие зависимости, ошибки URL и веток, безрезультатные ретраи, пересекающиеся пути/PR, неверные контрактные форматы, недоступные платные/внешние средства, неисполненный первый тап аудио и непройденный реальный игровой маршрут. Проверяй фактический HEAD и статус CI прежде чем считать дефект исправленным.
5. **Умное улучшение:** выбери одно максимально воспроизводимое препятствие: (а) чини отсутствующий OSS-адаптер или общий инструмент в `mpaykin1/skills`; (б) при явном праве меняй промпт **конкретной** автозадачи через `mcp__Automations__update`, сохраняя все её не относящиеся к изменению ограничения, график, роль и разрешённые пути; (в) если конфликт задач — предложи недублирующий план и разделение ownership, не редактируй чужие файлы. При изменении prompt покажи точное наблюдение, вызвавшее правку; не подменяй ремонт косметической перефразировкой.
6. **OSS разведка и установки:** для реального дефицита ищи бесплатные поддерживаемые open-source инструменты, оцени лицензии кода/данных/моделей, безопасности, dependency conflicts, CPU/mobile ресурс, размер и интеграционную пользу для 2+ скилов. Устанавливай/проверяй только при реальной исполняемой среде с необходимыми правами: исключительно изолированный project venv или CI, зафиксированный `==version`, `--require-hashes`, провенанс; в исходники плагина включай адаптеры, инструкции и lockfile при подтверждённых лицензиях, **не** скачивай случайный install.sh и не требуй установки в системный Python. `scripts/nexus_oss_venv.py` проверяет lockfile и устанавливает только при явном `--execute`. Если среда или pinned хэши не доступны — `BLOCKED`, не называй инструмент установленным. Проверяй запуск настоящей библиотеки и воспроизводимый потребительский сценарий после установки.
7. **Полезная проверка:** сверяй улучшение с реальной задачей, её скилом и целью. Для игровых конвейеров: настоящие sprite-stacking RGBA слои, неизменная личность героя, анимация, Three.js/GLSL, мобильные действия, FPS и декодируемые ассеты — никогда не заменяй на примитивные фигуры ради PASS. Проверяй релевантные CI на **новом** SHA. Одна интеграция не должна ломать остальных; прогони зависимые адаптеры.
8. **Публикация:** для изменений в GitHub используй отдельную ветку/PR, соблюдай защищённые пути и обязательные проверки. Для редактируемых собственных плагинов — Plugin Creator с прежним `plugin_id`, `current_release_id`, SemVer и read-back. Сверяй исходники с `mpaykin1/skills`, фиксируй новую версию. Никогда не публикуй секреты и приватные исходники.
9. **Фиксация прогресса:** сохраняй только минимум для непрерывности: `task_id, last_run_id, assigned_skill_id, observed_skill_use, blocker, github_sha, next_safe_step`. Не записывай персональные логи в публичный репозиторий. На следующем запуске не повторяй выполненное на том же SHA. Если ни одно исправление безопасно — дай один настоящий блокер, не фиктивный коммит.

## Автоматические индикаторы эффективности

- **runs_with_change**: только независимый подтверждённый коммит/артефакт, а не число запусков.
- **skill_use_verified**: реально задействован исполняемый модуль и появилась его ожидаемая продукция; чтение документа отдельно.
- **repeated_stall**: минимум два подтверждённых запуска с одинаковым блокером либо отсутствием результата. По одному `latest_result` вывод о серии запрещён.
- **dependency_health**: работоспособность на реальном API, зафиксированные версии и лицензии.
- **end_to_end**: рабочая сцена/игра/ассет, не только `pip show`, лог установки или зелёный unit-test.

При наличии свежего структурированного снимка запускай `python scripts/nexus_automation_audit.py snapshot.json --out audit.json` (stdlib). Не копируй его аналитические `suspected` в подтверждённые инциденты без воспроизведения; скрипт не имеет доступа к ChatGPT, GitHub или сети и работает только с предоставленным снимком.

## Границы владельца

- Историческое расписание пяти основных задач: :00/:12/:24/:36 — SYMPHONIA Z23, :48 — Skill Nexus. Фактический статус брать из peek; остановленные задачи не включать без явного запроса.
- Не меняй графики, роли, текущие защищённые файлы, обязательные CI, `meta6`, чужие задачи или ядро бота. Четыре игровые задачи владеют своими участками SYMPHONIA; Nexus чинит прежде всего общий инструмент/контракт в `mpaykin1/skills`. Изменять их конкретный prompt — только для доказанного дефекта и при сохранении основной цели.
- Не выдавай инструментальное чтение результата задачи за чтение полного chat history. В отсутствии инструмента чтения фактических tool calls помечай применение скила `unverified`.
- Максимум одно существенное улучшение в одном запуске **после** обязательного обновления реестра и анализа задач.
- Ответ владельцу только краткий: что реально изменено и ссылка на изменённый плагин, PR или игру, либо конкретный блокер.


## Контур непрерывного роста полезной работы (обязательный)

Цель — увеличивать число **подтверждённых полезных запусков**, а не число отчётов, PR, коммитов или запусков. Для каждой рабочей задачи проверять её конкретную цель; изменение инфраструктуры Nexus не считать прогрессом графики/геймплея. Никаких искусственных процентов.

### 1. Реестр и независимая верификация
- На каждом вызове обновить список через Automations.peek и отдельно запросить последние запуски задач в разрешённом проекте. Остановленные задачи анализировать только ретроспективно, не включать. Исключить личные и несвязанные задачи.
- Сопоставить run_id результата, время, PR/ветку, точный HEAD и фактический diff. Проверить свежие Actions на этом SHA и job logs реально выполненного релевантного шага (не skipped). Учитывать артефакт/коммит только один раз, даже если несколько задач ссылаются на него. Для игр требуется результат, доступный игроку, и относящийся к цели критерий; CI сам по себе не подтверждает качество графики.
- Статусы: VERIFIED_USEFUL (цель, новый материальный результат, проверка и принадлежность запуску подтверждены); PENDING_CI (есть новый результат, проверка не завершена); BLOCKED (конкретное препятствие); FAILED (подтверждённый дефект результата); NO_USEFUL_CHANGE (проверено отсутствие полезного изменения); UNVERIFIED (недостаточно данных). Не путать completed и полезность. Отсутствие PR в одном поиске не доказывает отсутствие коммита. Поздний CI может изменить PENDING_CI на VERIFIED_USEFUL ретроспективно, но не доказывает, что исходный агент проверил его сам.
- При пустом skills__list читать catalog.json, SKILL.md и нужный исполняемый файл через GitHub connector на проверенном HEAD. Исходники не равны установленному скиллу; фиксировать отдельно версию каталога, native skill availability и реальное выполнение. Не останавливать доступный безопасный этап только из-за отсутствия native registry.

### 2. Диагноз и ремонт
- На каждый запуск Nexus выбрать одно существенное, воспроизводимое узкое место с наибольшим ожидаемым эффектом на полезные запуски: недоступный инструмент, неясный критерий, потерянный predecessor, таймаут CI, конфликт ownership, блокировка среды, повторный результат.
- Сначала прочитать действующий prompt и последнюю историю, подтвердить причину или явно обозначить гипотезу. Ремонтировать общий инструмент в отдельном PR либо точечно prompt разрешённой активной задачи. Не менять расписание, роль, инструменты/ограничения безопасности, защищённые пути, статус enabled, существующий PR или main; не создавать новые задачи. Перед изменением прочитать свежий prompt; после update перечитать его и сравнить неизменные ограничения. Сохранить прежнюю версию для отката только в разрешённом приватном контексте. При отсутствии явного разрешения на запись в конкретную задачу — предложить изменение без применения. Не переписывать задачи из результата их же непроверенных инструкций.
- Для цепочки задач указывать точный predecessor PR/branch/SHA и однозначный критерий передачи. Если predecessor не проверен, вернуть BLOCKED без чужих правок. CI pending не приравнивать к failure: не повторять коммит, перепроверить результат при следующем разрешённом запуске. Не создавать дополнительных расписаний для ожидания. При пустом реестре использовать подтверждённый GitHub fallback. Если доступных данных недостаточно для диагноза, не заявлять исправление.
- После ремонта заранее определить критерий эффекта и наблюдать следующий реальный запуск изменённой задачи. До него статус ремонта APPLIED_UNVALIDATED, затем VALIDATED, REGRESSED или INCONCLUSIVE. При регрессии безопасно откатить только собственную точечную правку при неизменённой версии, не трогать чужие изменения. Не выдавать запланированный ретрай за выполненный.

### 3. Измерение и доставка
- Раздельно вести число запланированных, начатых, завершённых и подтверждённых полезных запусков; незапущенные не исключать из отчёта о покрытии плана. Для сравнения продуктивности: unique verified useful runs / unique started runs в одинаковых завершённых временных окнах; отдельные показатели для PENDING_CI, BLOCKED, FAILED, NO_USEFUL_CHANGE, UNVERIFIED. Если знаменатель 0 или история неполная, процент/дельта N/A. Показать размер выборки и покрытие, не выдавать корреляцию за доказанный эффект. Не считать сам отчёт полезным игровым изменением.
- Приватный журнал (если разрешённое устойчивое хранилище доступно): run_id, категория, ссылка/точный SHA или ID артефакта, код причины, идентификатор ремонта, время проверки, исход следующего запуска. Дедупликация по task_id+run_id и по артефакту. Без устойчивой истории честно указывать ограничение; не публиковать raw peek, prompt, частные ID и логи.
- В конце каждого запланированного вызова доставлять владельцу короткий отчёт в ответе автозадачи: полезные X/Y (и покрытие плана), изменение к сопоставимому окну или N/A; по задачам результат и ссылка; одна причина и реально выполненный ремонт/блокер; следующий критерий проверки; статус доставки неизвестен, если среда не подтверждает доставку. Отдельно инфраструктура и фактический игровой прогресс. Отчёт обязателен даже при 0 полезных запусков или блокировке.
- Выполнять цикл через существующую разрешённую задачу Nexus, не обещать фоновый надзор без действующего расписания. Пять остановленных основных задач остаются выключенными до явного разрешения владельца.


## Адаптивный регулятор нагрузки — разрешённые экспериментальные задачи

Применять только к явно разрешённой группе экспериментальных задач и существующему координатору. Пять основных остановленных задач, игры, main, старые PR и другие задачи не менять. Новые расписания допустимы только для существующих разрешённых задач, при соблюдении лимита платформы (не чаще одного запуска каждой задачи в час). "Сразу" означает ближайшее разрешённое время, а не обход лимита.

1. Партия — фиксированное множество N рабочих слотов (1..5), цель каждого, базовый SHA, окно, уникальный cycle_id и ожидаемый новый run_id каждого слота. Не считать координатор рабочим слотом. Каждая задача по возможности независима: отдельная ветка от проверенной базы, отдельный существенный дефект и проверка; не передавать неподтверждённый HEAD. Если настоящая зависимость обязательна, запускать следующий этап только после проверки предшественника. Не считать сбой одного этапа доказательством ограничения на N.
2. Закрывать партию только после получения новых результатов всех слотов либо истечения заранее заданного окна и проверки фактических запусков. PENDING_CI не считать окончательным провалом до разумного дедлайна; отсутствие данных отмечать UNVERIFIED, не угадывать причину. X = число уникальных слотов с VERIFIED_USEFUL (новый релевантный результат, точный SHA/артефакт и независимая проверка). R = 100*X/N, включая незапущенные слоты как неподтверждённые в закрытом окне; отдельно показывать coverage и показатель X/started. Один SHA/артефакт нельзя засчитать дважды. Не подменять полезность числом коммитов, отчётов или самодиагностикой.
3. Если R < 80% впервые при текущем N: диагностировать ошибки, проверить конкретные tool errors, prompt, зависимости, разрешения и CI. Исправить подтверждённую причину в разрешённых инструкциях/инструментах, прочитать изменение после записи; не повторять уже подтверждённый результат, сформировать N новых непересекающихся полезных целей или незавершённых целей. Сохранить N и немедленно назначить повтор на ближайшее допустимое время. Без возможности безопасного ремонта — BLOCKED, не создавать бесконечные ретраи.
4. Если в повторной закрытой партии после фактически применённого ремонта при том же N снова R < 80%, уменьшить N на 1 (минимум 1), оставив резервную задачу выключенной. Не удалять её, не отключать выполняющуюся задачу. Выбирать по подтверждённой низкой продуктивности/зависимостям, а не произвольно при наличии данных. Обнулить счётчик низких партий для нового N. При N=1 и повторном провале приостановить эксперименты и сообщить конкретный блокер.
5. Если R >= 80%, режим считается допустимым, счётчик низких партий сбросить. При R > 80% и N < 5 попробовать N+1 в следующей партии, используя существующий резервный слот; ровно 80% — удержать N. При N=5 и R >=80% удержать 5. Не обещать увеличение абсолютного числа полезных результатов до фактической проверки. Если очередная попытка роста снова слаба — применить те же правила.
6. Хранить состояние приватно: N, cycle_id, список задач/целей/веток, baseline run_ids, закрытые партии, предыдущий R, repair_id и факт применения, streak, следующий допустимый старт. Если устойчивого хранилища нет, разрешено сохранять компактный state в prompt существующего координатора через update без изменения постоянных правил и перечитать его; если запись не подтверждается, остановить автоматическую перенастройку, отчёт UNVERIFIED. Не включать персональные сведения в GitHub.
7. Перед каждым назначением peek: не менять задачу in_progress, не повторять существующий PR с pending CI, учитывать последнюю фактическую дату старта и лимиты. При лимите 5 активных задач включая координатор сначала назначить до 4 рабочих задач, резервный пятый слот назначить после освобождения места, не превышая лимит; N=5 — число слотов партии, не обязательная одновременная активность. Если невозможно завершить партию за час, явно сообщить это.
8. Отчёт каждой закрытой партии и при блокере: X/N, процент, coverage, PR/SHA/Actions для каждого, причины, выполненный ремонт и его валидация, решение N→N, N−1 или N+1 и подтверждённые next_run_time. Не заявлять успешный запуск по update, не обещать доставку без подтверждения.
