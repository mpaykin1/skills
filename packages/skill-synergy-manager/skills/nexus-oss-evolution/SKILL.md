# Skill Nexus — непрерывная эволюция open source

Этот модуль работает **внутри существующего Skill Nexus** (`skill-synergy-manager`), а не создаёт новый конкурирующий управляющий плагин. Он дополняет основной скилл и его настоящие адаптеры, не изменяет их без доказанной необходимости. Взаимосвязи и старые результаты см. в `../skill-synergy-manager/SKILL.md`, `assets/synergy-map.json`, `assets/verified-links.json` и `references/interop-protocol.md`. Метрики старых семи игровых скилов нельзя переносить на весь современный каталог.

## Цель и правило цикла

**Один запуск = одно реальное, воспроизводимое улучшение** одного конкретного скилла или общей межскиловой зависимости. Следующий запуск продолжает с последнего подтверждённого состояния. Не делать новую библиотеку там, где уже есть общий совместимый компонент. Не путать описанный план с рабочей интеграцией, подготовленный PR с опубликованной версией, компиляцию с тестом геймплея. При отсутствии явного разрешения изменять чужие репозитории, чужие плагины, расписания и приложения запрещено.

### 1. Живой инвентарь без потерь

1. Сверь `skills__list` (установленные модули), `mcp__Plugin_Creator__list_owned_personal_plugins` (личные плагины и версии, с полной пагинацией) и `https://github.com/mpaykin1/skills` / `catalog.json` (публичный источник для автоматизаций). Плагины с одинаковыми названиями не объединять без стабильных `plugin_id`; имена и версии считать изменяемыми. Отдельно фиксировать все внутренние модули, а также плагины, которые не принадлежат владельцу. Неполный обход = статус `inventory_incomplete`, не стирать прежний реестр.
2. Для каждого принадлежащего владельцу плагина инспектируй свежий `SKILL.md`, `plugin.json`, scripts, requirements, лицензии, экспортируемые форматы, используемые open-source исходники и существующие тесты через `get_plugin_files` (при необходимости archive). Не предполагай наличие кода по одному описанию.
3. Читай текущие инструкции и ограничения проекта: эталоны, protected paths, существующие активные задачи, актуальные ветки; не меняй их ради нового движка. Для GitHub всегда получай свежий HEAD/SHA перед записью.
4. Инвентарь должен различать `installed`, `source_only`, `integration_verified`, `gameplay_verified`, `needs_dependencies`, `blocked` и `unknown`. Публичная копия `mpaykin1/skills` может содержать только частичный снимок исходников; не заявляй, что все зависимости доступны для исполнения.

### 2. Автоматический выбор следующего улучшения

Для каждого скилла просканируй: конкретный сбой, отсутствующий функционал, узкое место FPS/памяти/размера, слабое качество 3D/анимации, потерю оригинального арта, несовместимые форматы, дублирующиеся движки, устаревшие и уязвимые пакеты, недостающие тесты, неудобство мобильного управления, проблемы публикации. Подтверждай дефекты текущим состоянием, а не устаревшими логами. Делай ротацию по всем скилам, но приоритет отдавай критической поломке и технологии, полезной нескольким скилам. Не отвлекай действующие задачи SYMPHONIA от их собственного приоритета: для общего надзора нужна отдельная явно разрешённая автоматизация.

Кандидатов оценивай до внедрения:
- реальные новые возможности и полезность для нескольких скилов;
- качество и постоянство оригинального изображения, 3D-объёма, анимации;
- совместимость с существующими открытыми библиотеками, лицензиями и API;
- размер, скорость и поддержка Windows/mobile/offline HTML;
- сопровождение, upstream-активность, воспроизводимая фиксация версии;
- безопасность, обратимость и стоимость (предпочтение бесплатным CPU-first решениям).

При равенстве — предпочитай наименьшее изменение с наибольшей доказанной выгодой. Не интегрируй «для количества». Вести очередь улучшений с `plugin_id`, первопричиной, кандидатами, целью, зафиксированным source commit, статусом, запретами и проверяемыми критериями готовности. Проверяй очередь на дубли перед каждым запуском.

### 3. Поиск и допуск open source

1. Ищи действительные upstream GitHub-репозитории, release notes, documentation, issues, existing maintained forks и альтернативы. Сравни минимум два проекта при доступности, затем выбери лучшего по измеримым характеристикам. Никогда не выдумывай версии, лицензии, графику, benchmark или ссылки.
2. До копирования кода проверь лицензию **файла и репозитория**, зависимости, разрешённость распространения ассетов/весов, атрибуцию и совместимость с конкретным продуктом. MIT/Apache-2.0/BSD предпочтительны, GPL/AGPL/LGPL/CC/нестандартные/неизвестные — отдельная проверка; отсутствует лицензия = нет разрешения на перепубликацию. Никаких пиратских ресурсов и секретов.
3. Закрепи версию релиза/commit SHA и, где возможно, SHA256 перенесённых файлов. Получай исходники из настоящего upstream, не переписывай их вымышленным «аналогом» и не называй заголовок в README интеграцией.
4. При отсутствии свободной совместимой лицензии, доступа к нужному GPU, бинарных весов, сборочного окружения или исходных ассетов останавливай интеграцию без ложного PASS. Можно выбрать другой реально доступный кандидат.

### 4. Интеграция: общая библиотека вместо копий

- Одна функциональность имеет **одного владельца**; остальные получают её через явный адаптер/контракт. Используй реальные входы/выходы `PNG RGBA`, sprite atlas, `GIF/WebM`, `stack.json` + RGBA-slices, `GLB/glTF`, `VOX/BBMODEL`, shader config, scene JSON и игру HTML/JS.
- Для каждой направленной связи записывай `source → target`, сохранение идентификатора объектов, версии, оси/масштабы/единицы, кадровую частоту, формат и требования к runtime; прописывай fallback и способ отключить новую возможность. При несовместимости не ломай существующий pipeline — отдельный адаптер, а не форк всей системы.
- **Sprite Stacking first для игр, которым он предназначен:** истинные независимые RGBA-срезы, физически узнаваемый объём, прозрачность, корректная глубина, слои для анимации, угол обзора, детерминированное воспроизведение; совмещай с Three.js/GLSL/WebGL2. Не подменяй срезы плоскостями с одной и той же картинкой или геометрическими примитивами. Не навязывай Sprite Stacking скилам, для которых он ухудшает результат.
- Сохраняй утверждённых героев, объекты, исходную палитру, материалы и индивидуальные дефекты текстур. Избегай повторов обложек, одинаковых зданий и персонажей, шаблонных паттернов. Новая версия не может самовольно изменять героя в анимации атаки/покоя.
- Игровое движение только по вводу, без самопроизвольных атак; честные hitbox/collision, PC и touch controls, sound/autoplay после пользовательского действия, адаптация ландшафт/портрет. Работоспособная сцена важнее витринного GIF.
- Проверяй конкурирующие renderer loops, shader defines, версии Three.js, Rapier, textures, CSG, lifecycle/cleanup, GPU budgets. Настоящее улучшение измеряется сравнением на исходном и новом арте.

### 5. Обязательный gate перед публикацией

На локальном/CI авторизованном окружении с реальными исходниками выполни, где применимо:
1. Проверку происхождения, SPDX/лицензий и отсутствия секретов; наличие upstream commit + checksum, запрет защищённых путей.
2. Детерминированную сборку и запуск исходного входа скила, не только проверку импорта пакета.
3. Реальный круговой путь экспорта/импорта между затронутыми скилами с неподменёнными пользовательскими ассетами.
4. Визуальную проверку сходства и уникальности: ключевые силуэты и персонаж не исчезают, нет 2D-обмана вместо объёма и повторяющихся паттернов.
5. Для анимации — стабильные направления/состояния/кадры, движения без скачков; для игр — ввод, столкновения, камера, прохождение; для WebGL2 — реальный браузерный рендер, а не Canvas fallback как подмена.
6. Замер FPS, памяти, размера/загрузки на целевой конфигурации; не писать «оптимизировано», если нет baseline и новых чисел. Мобильную реальную проверку отличать от эмуляции.
7. Проход существующего CI, сохранение обязательных quality gates. Красный gate = нет публикации как PASS. Не ослабляй проверки ради зелёного результата.

`python scripts/oss_upgrade_gate.py path/to/candidate.json --root path/to/root` может проверить структуру provenance/изменённых файлов/базовых gates. Скрипт **не выполняет** CI, лицензионную экспертизу или визуальную оценку и не заменяет их. Не выдавай заполненные вручную результаты за доказательство выполнения.

### 6. Синхронный релиз в ChatGPT и GitHub

1. Меняй только принадлежащий владельцу плагин и только по разрешённому запросу. `Plugin Creator`: `get_plugin_files` с актуальным `current_release_id` → исправленные исходники → корректный overlay-архив с сохранением всех остальных файлов и двух манифестов → `update_plugin` **того же** `plugin_id` с `expected_release_id`. Должна расти SemVer. Не создавай дубль плагина. Читай обратно и сверяй сохранённые файлы/версию.
2. GitHub: `mpaykin1/skills` как публичный исходный зеркальный каталог. Ветка с минимальными изменениями, проверка лицензий/секретов, PR и проверки перед слиянием в `main`; не переписывай `meta6`, эталоны, ядро бота или охранные workflow. Учитывай, что репозиторий может содержать неполный source snapshot: недостающие двоичные файлы отмечай явно, а не имитируй.
3. Для одной версии имя и SemVer на стороне плагина и в `catalog.json` должны совпадать; критические тексты `SKILL.md`, скрипты и права на код сверяй хешами. В `main` обновляй только после разрешённых checks и согласованного релиза. Сохраняй ссылки на конкретный `plugin_url`, GitHub commit/PR и источник upstream.
4. Если один канал недоступен, не заявляй синхронизацию. Сохраняй безопасный артефакт/PR, показывай блокер и не пытайся обойти права доступа. Если в ChatGPT уже обновлено, а GitHub заблокирован, ставь статус `out_of_sync` до восстановления (и наоборот). Не откатывай сторонние изменения.
5. После выпуска проверь доступность прямых ссылок, новый релиз и реальный импорт скила в следующем игровом цикле. Сохраняй rollback через версию/релиз и git ref. Считай готовым только то, что подтверждено.

### 7. Повторяемость, события и автоматизации

- При явном запросе «развивай скилы регулярно» настрой отдельную автоматизацию. Не переназначай существующие пять задач SYMPHONIA, не создавай шестую без разрешения или при лимите задач. Навыки не запускают таймеры самостоятельно: без расписания запускаются по вызову.
- Один запуск — одно реальное улучшение или честное установление проверенного блокера. На следующем запуске читай сохранённый прогресс, находи первую неполную работу; не выбирай ту же выполненную интеграцию повторно.
- Реагируй на security advisories, несовместимые новые версии, upstream breaking changes, истечение лицензии/весов, снижение FPS или сбой репозитория. Для критического сбоя важнее безопасный откат, чем обновление ради новизны.
- Не выдавай отчёты, тестовые журналы или handoff без просьбы пользователя; наружу — короткие ссылки только на действительно сделанное и текущий статус. История и provenance остаются в технических метаданных.

**Правило признания результата:** улучшение = код интегрирован + релевантные реальные проверки зелёные + сохранена исходная графика + версия из ChatGPT и GitHub установлена и сверена. До этого статусы `planned`, `implemented_unverified`, `verified_pending_release`, `out_of_sync` или `blocked`.

## 8. Обязательный проектный цикл и новые скилы — v1.0.0

Каждый плановый запуск до выбора OSS-пакета **обязательно** вызывает `../nexus-project-operator/SKILL.md`: полная свежая инвентаризация авторских плагинов включая новые, сверка GitHub каталога, обнаружение действующих игровых проектов и одна действительная правка назначенным скилом или общей библиотекой. Используй `scripts/nexus_catalog_sync.py` для осторожной записи проверенного полного снимка, сохраняя предыдущие строки и `plugin_id`. Новые плагины не считать автоматически перенесёнными на GitHub. Не конкурируй с четырьмя задачами SYMPHONIA за одни файлы.
