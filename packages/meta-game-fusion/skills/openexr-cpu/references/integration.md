# OpenEXR CPU archive — lossless scene-linear render interchange
OpenEXR official documentation: https://openexr.com/en/latest/ReadingAndWritingImageFiles.html ; OpenCV FP32 ZIP API: https://docs.opencv.org/4.10.0/d8/d6a/group__imgcodecs__flags.html . OpenEXR stores HDR, not a renderer or animation generator. The available CPU backend is OpenCV 4.13.0 built with OpenEXR 2.3.0; actual FLOAT32 ZIP read/write has been exercised on synthetic finite HDR RGBA data, with bit-exact roundtrip. Standalone OpenEXR 3.4.4 Python installation was unavailable. Do not claim a recent standalone SDK or full EXR feature support. Legacy decoder is restricted to trusted locally generated canonical archives only; do not use it on user-uploaded or external EXR. Prefer maintained reviewed OpenEXR/OpenImageIO on an isolated worker for external inputs and complex passes; verify package provenance and limits. No GPU or paid service. No new visual improvement claimed.

## Pipeline
OpenSubdiv and Rigify/NLA produce approved true 3D poses; Material Maker, OSL, MaterialX and Embree/Cycles CPU supply materials and illumination. Mantaflow/OpenVDB/NanoVDB supply real physical fire; do not use image archive as volume storage. OIDN CPU HDR denoising may precede archiving newly rendered candidates (not maps or approved sprites). Existing OIIO bridge selects explicit RGBA channels from EXR and creates meta-ocio-render-v1 straight float32 NPY recipe. Use that recipe, or actual equivalent linear render recipe, to archive with `python scripts/archive_exr.py export RECIPE.json NEW_DIR`. CPU OpenCV and NumPy required. Preserve all input bytes. Output single-part scanline FLOAT RGBA ZIP, unchanged alpha and HDR samples, bounded to 2048² per frame/240 frames, processed sequentially. Exact channel type/window/compression checks and bitwise readback are mandatory for each newly written EXR. No half conversion, no lossy codecs, no display transform. Reject additive zero-alpha RGB and unsupported inputs rather than losing values. Color space and straight-alpha convention reside in the paired JSON, not assumed from EXR headers; keep archive and sidecar together, do not use canonical straight EXR as a generic premultiplied compositing file. Use `python scripts/archive_exr.py audit RECIPE.json ARCHIVE` only on trusted self-generated archives with known provenance; hashes alone do not confer trust. Output oiio-recipe.json matches existing oiio-cpu/scripts/exr_bridge.py convert input. On worker with OIIO, re-import and independently compare original NPY bit patterns before OCIO. Use original NPY directly for OCIO when archive retrieval is unnecessary; avoid redundant conversion and never apply two display transforms. External EXR, deep/multipart/AOV, crop windows and signed color are outside this adapter. Keep original raw files. No automatic approval.
