## Extension boundary
`createTransport({joinRoom, gameId, roomId, sample, onState, onLeave, onError})` returns `getInterpolated`, `leave`, `room`, `ready`. The server adapter preserves the snapshot and lifecycle contract. Rapier collision simulation uses the shared physics module; only authority-owned state changes affect the shared world. No duplication of room or WebRTC stacks.

## Colyseus integration (1.1.0)
- Sources: https://github.com/colyseus/colyseus ; https://0-17.docs.colyseus.io/sdk ; https://0-17.docs.colyseus.io/room . Pinned legacy 0.17 family: server colyseus 0.17.11, client @colyseus/sdk 0.17.39. Install client in runtime and server in runtime/server independently; commit lockfiles only after successful install. Node 22. Do not claim installed/deployed from package declarations alone.
- `protocol.mjs` is shared by Trystero and Colyseus: avatar validation, sequence checks, interpolation, animation IDs; `session.mjs` selects the transport. Use `createSession({mode:'p2p',joinRoom,...})` or `await createSession({mode:'server',client,gameId,roomId,sampleInput,onSelf,onState,onLeave,onError,onDisconnect})` where `client=new Client(configuredHttpsEndpoint)` from @colyseus/sdk. `sampleInput` returns normalized dx,dz. `onSelf` reconciles local avatar with authoritative state. Omit roomId to create; share returned roomId and explicit mode for invite; join by exact ID. Never silently switch a live server session to P2P; offer a new separate co-op room only with explicit user choice.
- `runtime/server/index.mjs` is a minimal four-player authoritative movement room, 30 Hz simulation / 15 Hz full snapshots, Rapier capsule movement with static colliders, stale-input timeout, normalized axes, monotonic input sequence and per-player message throttling. It is NOT a full combat or dynamic-object server. Production must reuse game-specific collision and NPC simulation, authoritative damage, validated actions, authentication, rate limits, room creation limits and reconnection/resync. Room ID is not authentication. No paid hosting or deployment changes without authorization. GitHub Pages hosts client, not Node/WebSocket server. Use WSS/HTTPS and explicitly configured allowed origin at deployment; never expose debug admin endpoints.
- Both modes reuse renderer and animation assets. Server mode submits inputs, never accepts positions or combat outcomes from clients. P2P mode remains opt-in for casual friends, no competitive scores. Do not run both transports for the same room. Use shared protocol and render buffer; Rapier replaces the planar step, not the transport. Local movement prediction is optional and must reconcile with authoritative snapshots.

## Rapier integration (1.2.0)
- https://github.com/dimforge/rapier.js ; https://rapier.rs/docs/user_guides/javascript/character_controller/ . Pin @dimforge/rapier3d-compat 0.19.3 in both runtime packages; initialize WASM before creating worlds. `physics.mjs` accepts initialized Rapier explicitly so Node and browser resolve their own dependencies. 30 Hz fixed timestep, normalized input, gravity, capsule controller, static obstacle sliding, bounded demo arena, deterministic spawn slots, disposal. Feet coordinates in shared snapshot; body center stays internal.
- Colyseus calls this physics module for server-authoritative movement; snapshots remain 15 Hz and clients render through existing buffer. Client may not submit world geometry, transforms or damage as truth. The demo map is not any existing META level. For a real game, supply identical versioned collision geometry from trusted level assets on server and client; use approved assets for visuals and match colliders. Reject mismatched build hashes before joining production rooms.
- For P2P opt-in use `createSession({mode:'p2p',localPhysics:{R:Rapier,boxes,spawn}, ...roomOptions})`; drive `advancePhysics(deltaSeconds,{dx,dz})` once from the existing loop, `sampleLocal()` for local visual transform; adapter sends the same snapshot as before. Omit localPhysics when game already uses Rapier; adapt existing sample instead. Solo can use `createLocalPhysics` directly. Never run two movement simulations on one actor. Remote avatar visuals are not colliders in this demo. P2P remains non-authoritative and cannot guarantee cross-client agreement or prevent cheating.
- Dynamic vehicles, rigid bodies, player-v-player contacts, jumping, combat, host migration and prediction/reconciliation are not implemented by this demo. Extend through shared authority-owned world state, stable IDs and fixed tick; never simulate authoritative remote objects independently. Preserve Sprite Stacking animation frame IDs.

## Nakama social integration (1.3.0)
- Sources: https://github.com/heroiclabs/nakama ; https://github.com/heroiclabs/nakama-js ; https://heroiclabs.com/docs/nakama/client-libraries/javascript/ ; https://0-17.docs.colyseus.io/auth/room . Pin browser SDK @heroiclabs/nakama-js 2.8.0. Nakama server and PostgreSQL must be independently provisioned, version-pinned and secured; do not start paid services. GitHub Pages cannot host either backend.
- `runtime/nakama-social.mjs`: `createSocial({host,port,serverKey,secure:true})` authenticates with an opt-in random device UUID, gets profile, lists/adds friends, reads/writes private casual saves with optimistic version checks, reads pre-created leaderboards, and generates token-free invite URLs via `makeInvite`. Use `crypto.randomUUID()` once and retain device credential privately; no fingerprinting. Link a recovery login before relying on device identity across devices. Session lives in memory in wrapper; inspect SDK auth storage and clear tokens on logout, never embed them in invite, logs, source or analytics. Browser serverKey is the public client authentication key, never console/runtime/session secret. Use configured trusted HTTPS origins and no default production keys.
- `social.openAccountRoom({client:new ColyseusClient(trustedEndpoint),gameId,roomId,matchmaking,sampleInput,onSelf,onState,onLeave,...})` uses dedicated Colyseus client and Nakama access token. `server/nakama-auth.mjs` calls GET /v2/account on fixed NAKAMA_API_ORIGIN with Bearer token, timeout and fail-closed validation. No trusting userId or decoding JWT without verification. Private server-to-server HTTP only on isolated trusted network; production public endpoints HTTPS/WSS. Do not expose database or Nakama console. Reauthentication/expiry enforcement mid-game, account recovery and abuse quotas require production integration.
- When NAKAMA_API_ORIGIN is configured, server defines separate `meta-account-v1` with queue/gameId/protocol filters. Public queue uses Colyseus joinOrCreate; private invite uses create + exact room ID, with setPrivate and matching queue; duplicate account in same room rejected. Invite with queue=public must be joined with matchmaking:true. No parallel Nakama realtime gameplay socket or duplicated physics. Native Nakama matchmaker/ELO matching not implemented; Colyseus fills compatible rooms using Nakama-verified account admission. Guest meta-v1 remains separate demo and has no competitive authority. Trystero remains optional P2P with social layer only for profile/friends/casual saves, not verified remote identity. Account-backed room ID is not an ACL; production private-room access needs server-owned invitation grants.
- Scores are read-only until actual game-specific server completion events and idempotent server-to-server Nakama writes are integrated. Create authoritative leaderboard on Nakama and reject client writes. Never accept P2P or casual save scores, inventory or unlocks as trusted. Never invent a leaderboard or claim competitive support from demo movement. Preserve existing Rapier controller and shared snapshots unchanged.
- Deploy only in approved sandbox; verify real account authentication, refusal of expired/forged token and wrong game/queue, matching, invite joins, two-device physics, save conflicts and leaderboard permissions before claiming working multiplayer. Do not include private credentials or raw evidence in user response.
