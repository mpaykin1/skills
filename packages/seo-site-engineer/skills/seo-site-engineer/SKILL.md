# SEO Site Engineer — рабочий скилл

## Цель
Доводить SEO существующего сайта до проверяемого результата: от аудита исходников и опубликованных URL до исправлений, CI, безопасного слияния и повторной проверки публичной страницы. Не подменять выполнение отчётом. При отсутствии доступа к сайту/репозиторию выдавать только проверяемые рекомендации и готовые изменения, не заявлять об их публикации.

## Порядок выполнения
1. Определить домен, репозиторий, основную ветку, CMS/статический генератор, локализации, тип страниц, приоритеты и доступные инструменты. Проверить действующие AGENTS.md, ограничения, владельческие правила, защищённые пути, открытые PR и существующие SEO-проверки. Не менять чужие защищённые файлы.
2. Снять базовую картину: публичный HTTP-статус, robots.txt, sitemap, canonical, meta robots, title/description, H1/H2, контент, внутренние ссылки, изображения, JSON-LD, Open Graph, мобильную версию, Core Web Vitals (если измеримы), индексируемость и дубли. Разделять «не проверено», «проверено», «исправлено», «опубликовано».
3. Составить матрицу URL → интент → title → description → canonical → индексируемость → schema → контент → изображения → внутренние ссылки. Не выдумывать факты, статистику, поисковый трафик или игровой процесс.
4. Исправить критические ошибки: HTTP 404/5xx, ошибочные canonical, noindex на продакшене, индексируемые дубли/preview, битые ссылки, отсутствующие обязательные метаданные, некорректную структурированную разметку.
5. Для каждой индексируемой страницы сделать уникальные и полезные title (ориентир до 60 символов) и description (ориентир 120–160 символов, не жёсткие ограничения поисковиков), один понятный H1, содержательный текст под реальный интент, точные alt, релевантные внутренние ссылки. Не делать keyword stuffing и шаблонный контент.
6. Для каталогов игр: самостоятельная страница каждой реально отличающейся игры, описание 150–300 слов как редакционный ориентир, реальные механики и проверенное управление, 2–3 собственных оптимизированных WebP/AVIF-кадра, локальная OG-обложка. Три видимых FAQ только если вопросы реально полезны; FAQPage JSON-LD должна точно повторять видимые ответы. FAQ rich results не обещать.
7. Создать/обновить Schema.org (WebSite/Organization, BreadcrumbList, CollectionPage, VideoGame, Article — только где уместно), валидировать JSON и обязательные поля; не маркировать несуществующие отзывы, рейтинги и свойства.
8. Поддерживать sitemap только из канонических индексируемых опубликованных URL; lastmod — реальная дата содержательного изменения. Preview — noindex и исключён из sitemap; robots.txt не должен скрывать noindex от робота. Не выдавать успешный CI за HTTP 200.
9. Для многоязычного сайта: отдельные реальные переводы, корректные hreflang/x-default, взаимные ссылки, язык страницы, региональность только по факту. Не генерировать фиктивные переводы.
10. Улучшить загрузку: локальные сжатые изображения, width/height, lazy-loading ниже первого экрана, приоритет LCP, отсутствие ненужных CDN, проверка mobile usability. Не ломать игру и дизайн ради SEO.
11. Проверить IndexNow только если поисковая система и сайт его поддерживают: доступность ключа на хосте, host/keyLocation, отправка только реально изменённых опубликованных URL после деплоя, HTTP 200/202 от API. Не утверждать, что IndexNow гарантирует индексацию или охват Google.
12. Перед PR прогнать существующие проверки и новые негативные сценарии. Если репозиторий требует контур К1–К12, минимум три мутации на новую проверку, включая обходной сценарий; не ослаблять охранников. Не менять исходники игр/эталонов для косметического SEO.
13. Создать небольшой PR, проверить обязательные CI на актуальном SHA, соблюдать правила ревью/слияния. После публикации отдельно проверить живой HTTP 200, canonical, robots, JSON-LD, изображения, ссылки и sitemap. Не объявлять задачу завершённой при красных проверках.
14. Сохранить контрольную точку прогресса в существующем трекере проекта, если он есть. Повторный запуск продолжает с незавершённого шага, не дублируя сделанное.

## Контроль качества
Верифицировать каждую правку по трём уровням: локальная структура → CI на текущем SHA → опубликованный HTML. Любое утверждение о публикации подтверждать живым ответом, а не ссылкой на исходник. При недостатке данных указывать конкретно, что не удалось проверить.

## SiteOne Crawler — обязательная интеграция v1.1
Перед новым техническим SEO-циклом и после публикации использовать [SITEONE.md](references/SITEONE.md) и исполняемый адаптер `scripts/siteone-audit.py`. SiteOne выявляет узкие места на уровне всего сайта; SEO Site Engineer исправляет их; Web Performance измеряет браузерные ограничения; повторный обход контролирует регрессии. Сохранять существующие проверки и правила. Не подменять реальные данные предположениями. При отсутствии установленного бинарника или сети явно назвать блокер и использовать доступные независимые источники. Не создавать новый PR, если достаточно довести уже готовый пакет до публикации. Не включать платные API без разрешения.

## Lighthouse CI — обязательное усиление v1.2
SiteOne определяет проблемные URL и полноту обхода; Lighthouse CI измеряет мобильный браузер на этих URL; Web Performance исправляет LCP, CLS, TBT и доступность; повторный SiteOne и Lighthouse контролируют регрессии. Использовать [LIGHTHOUSE.md](references/LIGHTHOUSE.md) и `scripts/lighthouse-audit.py` на главной, страницах основных типов и изменённых URL. Не называть лабораторный TBT реальным INP. Не отправлять отчёты в публичное хранилище, не устанавливать зависимости непроверенными скриптами, не отключать существующие CI. При недоступной публикации не накапливать новые PR вместо завершения переноса.

## Web Vitals — полевые метрики v1.3
Следовать [WEB-VITALS.md](references/WEB-VITALS.md). SiteOne определяет проблемные канонические URL, Lighthouse CI изолирует лабораторные причины, Google web-vitals измеряет LCP/INP/CLS в реальных сессиях, Web Performance выбирает исправления; после исправления повторить оба аудита и сопоставить независимые полевые окна p75. Использовать `scripts/vitals-client.mjs` и `scripts/vitals-aggregate.py`. Не внедрять телеметрию без явного разрешения на сбор, проверенного first-party приёмника, согласия там, где оно требуется, и политики хранения. GitHub Pages не является POST-приёмником; при его отсутствии использовать CrUX/Search Console при наличии данных, либо локальное измерение без отправки. Не считать лабораторный TBT реальным INP, отсутствие данных — улучшением, синтетические записи — полевыми измерениями. В KILLKLAN никогда не отправлять пользовательский поисковый запрос, полный URL с query/hash, текст, идентификатор пользователя или данные аудио.
