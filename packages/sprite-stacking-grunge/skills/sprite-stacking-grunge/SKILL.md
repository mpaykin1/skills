# Sprite Stacking Grunge Horror

## Художественный стандарт (обязателен)
Grunge Horror. Постапокалиптический стиль с физически достоверными пропорциями. Состаренный металл, выцветшая серо-синяя краска, хаотичная ржавчина, грязь, царапины и вмятины. Приглушённая палитра, глубокие чёрные тени, тусклые металлические блики. Зернистая живописная фактура. Выраженный трёхмерный объём. Без мультяшности, вокселей, пиксельной сетки, чистых поверхностей и повторяющихся паттернов. Игровой спрайт на прозрачном фоне. Для неметаллических объектов — соответствующие правдоподобные состаренные материалы (кожа, дерево, ткань, камень), без искусственной металлической подмены. Стиль не заменяет форму исходного референса.

## Вход и процесс
1. Пользователь сообщает только название/описание объекта, при желании прикладывает референс. Самостоятельно выбери масштаб, конструкцию, материалы и движения. Если дан эталон, сохраняй его силуэт, цвет, конструкцию, детали, пропорции и идентичность; неизвестные стороны реконструируй согласованно, не выдавая догадку за точную копию.
2. Создай художественный образ инструментом генерации изображений при необходимости. Для настоящей многовидовой сборки создай единый текстурированный 3D-источник (например Blender mesh с UV и материалами) или вручную сформируй согласованные послойные сечения. Если есть исходная сетка, используй её. Не выдавай набор независимо нарисованных ракурсов за срезы. Не выдавай экструзию одной картинки за полную 3D-реконструкцию.
3. Разрежь объём горизонтальными сечениями по Z снизу вверх. PNG RGBA одинакового размера, общая система координат и pivot, прозрачность вне объёма. Каждый срез содержит реально существующую геометрию на своей высоте, отверстия и раздельные части сохраняются. При сэмплировании сетки используй UV и цвет ближайшей поверхности для внешних граничных вокселей, корректный inside/outside, тонкие элементы не должны исчезнуть. Материалы и фактура закреплены в локальных координатах, свет не запечён по-разному в каждом ракурсе. Не нарезай плоский PNG на полосы, не клонируй одинаковые слои. Подбери разрешение XY и шаг Z по минимальной видимой детали; ориентир 64–128 срезов для сложного объекта, 256–512 px XY; адаптируй под бюджет памяти, не превращай визуал в кубики. При необходимости повышай разрешение, рендери с supersampling и сглаживанием.
4. Сохрани исходник, PNG-срезы и stack.json. Схема: {"layers":["layers/000.png",...],"spacing":[dx,dy,dz],"pivot":[x,y,z],"size":384}; единицы произвольные, но едины. Оси +X вправо, +Y вперёд (верх PNG), +Z вверх. pivot в мировых единицах от геометрического центра объёма. Каждый срез — центр ячейки; нижний первым. Для частей на шарнирах допускается отдельный стек на часть и жёсткое преобразование; не деформировать спрайт, не менять размеры деталей. Для движущихся органических объектов допускается отдельный полный согласованный стек на ключевую позу, либо деформируемый исходный mesh с нарезкой каждой позы. Для камеры поворачивай один и тот же стек.
5. Собери PNG и GIF непосредственно из всех слоёв, используя scripts/render_stack.py (Python, Pillow, NumPy) или эквивалентный глубинно-корректный рендер. Не заменяй его другим красивым GIF. Скрипт поддерживает истинную видимость в объёме на любом азимуте и наклоне, включая строго сбоку, сверху и снизу. Рендер с фиксированным pivot/масштабом, ортографически по умолчанию, с единым фоном alpha=0. Скрипт не рисует материалы и не реконструирует геометрию автоматически: он собирает уже созданные срезы. Не объявляй полноценный результат до создания качественных срезов и фактической сборки.

## Ракурсы и анимация
- Полный оборот 0–360° с шагом не более 10°, по умолчанию 36 кадров; замкнутый цикл без дублирования конечного кадра. Дополнительно верхний, нижний, фронтальный, задний и оба боковых ракурса, диагонали; полярные виды ±90°. GIF обзор по сферической траектории без скачков, отдельные PNG ключевых видов. Не зеркалить асимметричный объект.
- Оружие от первого лица: направление от игрока +Y, две одинаковые руки с постоянным хватом. Нейтраль → вправо до полного бокового профиля → нейтраль → влево → нейтраль → вверх → нейтраль → вниз → нейтраль; вращение модели/камеры в 3D, а не поворот плоской картинки. Обзор 360° отдельно. Движение частей по физически правдоподобным суставам. Никакой самопроизвольной атаки.
- Транспорт, механизм, существа: отдельно обзор 360° и требуемые движения (вращение колёс, створки, ходьба и т.п.), используя один эталон. Состояния разрушения — изменённые детали исходника, не другая модель.
- GIF 20–30 кадров/с при возможности; прозрачность GIF бинарная, PNG сохраняют полный alpha. Не масштабируй/центрируй кадры отдельно. Не меняй свет или текстуру от кадра к кадру.

## Обязательный результат
- Сразу показать в чате фактически собранный из всех срезов анимированный GIF (если интерфейс не воспроизводит, дать прямую ссылку на тот же файл и честно отметить ограничение). Отдельные GIF движений и полный обзор 360°.
- ZIP: исходные прозрачные PNG-срезы, stack.json, ключевые ракурсы PNG, GIF, исходник геометрии/материалов если создан, код сборки. Не подменять файлами-заглушками. По запросу автономный HTML без CDN с реальным объёмным рендером, управление мышью/тачем, yaw/pitch, без подмены GIF-плоскостью. Не публиковать в чужих репозиториях без запроса.
- До выдачи визуально просмотреть ракурсы, убедиться в непрерывности движения, постоянстве формы, отсутствии обрезки, скачка pivot, дрожания текстуры, повторяющихся паттернов, пустых/дублирующих кадров. Проверить все слои входят в сборку, размеры и шаг согласованы. Не выдавать отчёт, тесты или evidence без запроса. При неполной готовности явно обозначить, что отсутствует.
- Интеграция Three.js: использовать реальные RGBA-срезы в локальных XY-плоскостях с шагом Z, корректной глубиной и alphaTest/depthWrite для непрозрачной маски; для вида строго вдоль плоскостей и полупрозрачных материалов использовать объёмный raymarch или многовидовые атласы, созданные из этого же стека. Не утверждать, что одни XY-плоскости без альтернативы корректны на всех углах. Для игры сохранять один pivot, физические коллайдеры и раздельные движущиеся части. Поддерживать мобильный FPS через согласованные LOD, а не подмену объекта.
