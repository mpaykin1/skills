# META GAMES — Catalog Updater v1.2.0

## Цель и обязательные правила

- Единственный каталог: https://mpaykin1.github.io/meta6/playgama-catalog/; публикация из `mpaykin1/meta6/playgama-catalog/`. Не путать с `meta6-lab/preview/claude-games/`.
- Один клик — одна игра: обложка, название, «Играть» новой карточки ведут непосредственно на один точный `https://playgama.ai/play/<siteId>`; `target="_blank" rel="noopener noreferrer"`. Не создавать `/games/<slug>/`, альтернативный запуск, вторую кнопку или переход через описания.
- Новая игра первая во всех 8 главных локалях (EN, RU, DE, FR, JA, KO, ES, PT-BR) и релевантных существующих жанрах. Не изменять порядок, ссылки и изображения старых игр.
- Обложка настоящая: предоставленная пользователем или подтверждённая официальная обложка именно этой игры. При уже сохранённой обложке использовать её; не спрашивать файл повторно. Не подменять градиентом, заглушкой или чужим постером. Проверять декодирование, размеры, видимость и HTTP 200. Загружать реальные байты исходного файла или проверенного перекодирования; никогда не придумывать base64.
- Права: всегда читать свежие `mpaykin1/meta6/AGENTS.md`, `mpaykin1/meta6-lab/AGENTS.md`, `GPT.md`, `rules/09-platforma/KATALOG_META_GAMES_PLAYGAMA.md`, действующую ПЕСОЧНИЦУ. Технический доступ GitHub не отменяет правило «ChatGPT не пишет в meta6»; при действующем запрете редактировать только MGL и готовить изменения разрешённому публикующему агенту. Не обходить веточную защиту или CI. При разрешённой публикации сделать её без перекладывания работы на пользователя.
- Не изобретать название, геймплей, Playgama ID или факт модерации. Предоставленная владельцем ссылка позволяет подготовить прямую карточку; статус Developer Console записывать отдельно, без подмены владельческого подтверждения.
- Минимум ручной работы. Не создавать handoff, evidence и отчётные файлы без просьбы. Не обещать фоновую работу: действия выполнять в текущем запуске.
- Обязательный протокол [PAGES_RELIABILITY.md](references/PAGES_RELIABILITY.md) при каждой публикации и жалобе «не вижу игру». Не отправлять владельца в GitHub Actions, если данные можно получить через подключённый GitHub API. Не повторять старый деплой и не делать пустые коммиты вместо диагностики.

## 0. LIVE-FIRST: исключить ложную «не опубликовано» и дубли

1. Из запроса извлечь точный Playgama URL, имя (если известно), обложку. Не задавать повторные вопросы о доступных данных.
2. Первым делом открыть опубликованный сайт и проверить HTML с `Cache-Control: no-cache` + `?rev=<SHA-or-timestamp>`; отдельно обложку, 8 локалей и sitemap. При наличии терминала использовать `python3 scripts/verify_live.py --game-url 'https://playgama.ai/play/...' --title '...' --slug '...'`; иначе HTTP/browser tools или GitHub Actions `Publish complete META6 site` с логом `curl` и `cmp` для конкретного SHA. Не путать main с публичным сайтом.
3. Читать свежие GitHub main: `playgama-catalog/playgama-inventory.json`, все 8 index.html, соответствующие жанры и последний deploy. Найти URL по siteId, не только title/slug. Проверить инвентарь и первую карточку. Если URL уже есть, не создавать дубль, а проверить/починить отсутствие, ссылку, обложку, жанры, HTML, SEO.
4. Если на live есть правильная карточка, обложка и ссылки — дать ссылку, ничего не коммитить. Если исходники содержат игру, а live ещё нет — диагностировать workflow и устранить задержку/ошибку в пределах разрешений. Если live недоступен, использовать точный CI-лог и обозначить пределы проверки; если нет и такого подтверждения, сказать «код в main подтверждён; live недоступен для независимой проверки», не утверждать, что игра отсутствует.
5. Отделять source_added, pr_open, pr_merged, pages_deployed, live_verified. Только live_verified означает «опубликовано в каталоге». Playgama DRAFT/ACTIVE/VISIBLE — отдельная ось.

## 1. Если игра действительно отсутствует

1. Подтвердить точную официальную ссылку Playgama и название; обложку брать из предоставленного изображения или официального источника. Не запрашивать повторно данные из текущей/доступной предыдущей беседы, использовать файл из репозитория, если есть.
2. Считать актуальные записи каталога: `index.html`, `ru/`, `de/`, `fr/`, `ja/`, `ko/`, `es/`, `pt-br/`. Не фиксировать число карточек константой. Не создавать существующие пути. Учитывать разные шаблоны `article.game-card` и `article.card`, включая карточки без дополнительных классов.
3. Подготовить 8 согласованных переводов tag, description, alt, aria, seo без выдуманного геймплея. Обложка в `playgama-catalog/covers/<slug>.webp|png|jpg`, проверить качество и размеры.
4. На всех 8 главных страницах добавить карточку первой; три ссылки на один URL. Сохранить прежние игры, их относительный порядок, лор «Зерно последнего мира» и ссылки на локализованные lore.html.
5. Обновить только релевантные существующие `genres/action|arcade|adventure|horror|story` во всех локалях; счётчики по DOM, ItemList.numberOfItems, позиции и SEO/OG/Twitter/canonical/hreflang/x-default. Sitemap содержит только собственные реальные страницы и lastmod по фактической дате, не внешнюю ссылку Playgama.
6. Сохранить все games, pendingGames, статусы, источники, старые URL. Для URL от владельца допустима pendingGames с честной пометкой owner supplied, без притворной Developer Console-верификации. Идентификатор ссылки — главный ключ от дубликатов.
7. Использовать `scripts/catalog.py add --root <repo> --game <json> --image <owner-cover>`, `scripts/catalog.py verify --root <repo> --game <json>` при локальном checkout. Скрипт не пушит. Иначе минимальные изменения через GitHub API с атомарным деревом/коммитом на отдельной ветке. Не считать examples/game.json настоящим релизом.

## 2. Публикация: довести до доступного разрешённого результата

1. Перед записью проверить права и актуальные ограничения. При разрешении создать ветку с текущего main, записать только целевые страницы, инвентарь, постер и sitemap, открыть PR и провести проверки без ослабления охранников. Не оставлять PR как «опубликовано». Использовать законный merge/автоматику, но не включать auto-merge вопреки правилам.
2. Если разрешён только MGL — полный минимальный PR/патч в MGL; найти существующий разрешённый механизм продвижения в MG, использовать без просьбы повторять данные. Если механизма нет, назвать конкретный блокер. Не путать доступ с разрешением.
3. После разрешённого merge/push читать main SHA и `Publish complete META6 site` (`.github/workflows/meta6-pages.yml`), конкретный run с head SHA, success и шаг `Confirm live games, SEO catalog and sitemap revision`: actual curl -fsSL с ?rev=SHA и cmp с build _site. Получать все запуски через GitHub GET `/repos/mpaykin1/meta6/actions/runs`, фильтровать по workflow, ветке и head SHA. PR-only выдача не охватывает push/dispatch. Без live-content проверки success недостаточен.
4. Проверить все 8 живых страниц: новая карточка первая и единственная, обложка HTTP 200 и декодируется, три ссылки ведут точно в Playgama; JSON-LD, число карточек согласованы, sitemap HTTP 200, релевантные жанры обновлены. Проверить mobile view/клик, когда браузер доступен. CI только для EN и sitemap не заменяет остальные проверки. Если live не обновился — чинить deploy/cache, не повторять add.
5. При сбое выполнить [PAGES_RELIABILITY.md](references/PAGES_RELIABILITY.md): автоматически прочитать jobs, steps, logs, artifacts; классифицировать причину, при разрешении устранить её и проверить новый SHA. Не менять источник Pages, не запускать старую ревизию, не просить скриншоты, если доступны API.
6. После успеха дать одну кликабельную ссылку на каталог (с ревизией при необходимости). При незавершённой работе не использовать «опубликовано» и фиктивную ссылку на результат; дать точный статус и ближайший блокер.
