# META GAMES — Catalog Updater v1.1.0

## Цель и обязательные правила

- **Единственный каталог:** https://mpaykin1.github.io/meta6/playgama-catalog/; публикация из `mpaykin1/meta6/playgama-catalog/`. Не путать с `meta6-lab/preview/claude-games/`.
- **Один клик — одна игра:** обложка, название, «Играть» новой карточки ведут **непосредственно** на один точный `https://playgama.ai/play/<siteId>`; `target="_blank" rel="noopener noreferrer"`. Не создавать `/games/<slug>/`, альтернативный запуск, вторую кнопку или переход через описания.
- **Новая игра первая** во всех 8 главных локалях (EN, RU, DE, FR, JA, KO, ES, PT-BR) и релевантных существующих жанрах. Не изменять порядок, ссылки и изображения старых игр.
- **Обложка настоящая:** использовать предоставленную пользователем или подтверждённую официальную обложку именно данной игры. При уже сохранённой обложке в репозитории использовать её; не спрашивать файл повторно. Не подменять CSS-градиентом, заглушкой или чужим постером. Проверить декодирование изображения, размеры, видимость и HTTP 200.
- **Права:** всегда читать свежие `mpaykin1/meta6/AGENTS.md`, `mpaykin1/meta6-lab/AGENTS.md`, `GPT.md`, `rules/09-platforma/KATALOG_META_GAMES_PLAYGAMA.md`, действующую ПЕСОЧНИЦУ. Подключённые GitHub API дают технический доступ, но сами по себе не отменяют правило «ChatGPT не пишет в meta6»; при действующем запрете редактировать только MGL и готовить изменения разрешённому публикующему агенту, не выполнять запрещённый push/merge. Не обходить веточную защиту или CI. Если правила разрешают прямую публикацию — сделать её без перекладывания работы на пользователя.
- Не изобретать название, геймплей, Playgama ID или факт модерации. Предоставленная владельцем ссылка позволяет подготовить прямую карточку; статус Developer Console записывать отдельно, без подмены владельческого подтверждения.
- Минимум ручной работы. Не создавать handoff, evidence и отчётные файлы без просьбы. Не обещать фоновую работу: все действия выполнять в текущем запуске.

## Алгоритм: сначала выявить действительное состояние, потом менять

### 0. LIVE-FIRST: исключить ложную «не опубликовано» и повторные добавления

1. Из запроса извлечь точный Playgama URL, имя (если известно) и обложку. Если ссылка предоставлена в текущем контексте — **не задавать о ней вопрос повторно**.
2. **Первым делом** открыть опубликованный сайт и проверить его HTML с `Cache-Control: no-cache` + `?rev=<SHA-or-timestamp>`; отдельно обложку, 8 локалей и `sitemap.xml`. При наличии терминала использовать `python3 scripts/verify_live.py --game-url 'https://playgama.ai/play/...' --title '...' --slug '...'`; при отсутствии — HTTP/browser tools или GitHub Actions `Publish complete META6 site` с логом, где проверено содержимое live через `curl` и `cmp` для конкретного SHA. **Не путать проверку `main` с публичным сайтом.**
3. Параллельно/затем читать свежие GitHub `main`: `playgama-catalog/playgama-inventory.json`, все 8 `index.html`, соответствующие жанры и последний deploy. Найти URL по **siteId**, а не только title/slug; проверить, что ссылка входит в инвентарь и карточка стоит первой. Если URL уже есть, не создавать дубль, а проверить/починить отсутствие или ссылку, обложку, жанры, HTML, SEO.
4. **Если на live есть правильная карточка, обложка и ссылки** — работа по публикации завершена. Сразу дать ссылку на каталог, ничего не коммитить и не заявлять об ошибке скилла. Если исходники содержат игру, а live ещё нет — продолжить проверку текущего GitHub Pages workflow и устранить публикационную задержку/ошибку до разрешённого состояния. Если live нельзя прочитать, сказать ровно «код в main подтверждён; live недоступен для независимой проверки», не утверждать, что игра отсутствует.
5. Отделять `source_added`, `pr_open`, `pr_merged`, `pages_deployed`, `live_verified`. **Только `live_verified` означает «опубликовано в каталоге».** Внешний статус Playgama (`DRAFT`/`ACTIVE`/`VISIBLE`) — отдельная ось.

### 1. Если игра действительно отсутствует

1. Сначала подтвердить точную официальную ссылку Playgama и название; обложку брать из предоставленного в запросе изображения либо официального проверенного источника. Не просить повторно уже предоставленное в этой или доступной предыдущей беседе. Если файл есть в репозитории, использовать его.
2. Считать актуальные записи каталога: поддерживаемые локали — `index.html`, `ru/`, `de/`, `fr/`, `ja/`, `ko/`, `es/`, `pt-br/`. Не фиксировать число карточек константой (14/17/18 — исторические цифры). Не создавать уже существующие пути.
3. Подготовить 8 согласованных переводов `tag`, `description`, `alt`, `aria`, `seo`, не приписывая игре неподтверждённый геймплей. Обложку хранить в `playgama-catalog/covers/<slug>.webp|png|jpg`, проверить качество и реальные размеры.
4. На всех 8 главных страницах добавить карточку первой; три ссылки на один Playgama URL. Сохранить существующие игры и их относительный порядок, лор «Зерно последнего мира» и ссылки на локализованные `lore.html`.
5. Обновить только релевантные существующие страницы `genres/action|arcade|adventure|horror|story` во всех локалях. Обновить счётчики по DOM, `ItemList.numberOfItems`, позиции и SEO/OG/Twitter/canonical/hreflang/x-default. Sitemap содержит **только собственные реальные страницы** и `lastmod` по фактической дате, не внешнюю ссылку Playgama.
6. Сохранить в инвентаре все `games`, `pendingGames`, статусы, источники и старые URL. Для URL от владельца допустима `pendingGames` с честной пометкой «owner supplied», без притворной Developer Console-верификации. Идентификатор ссылки — главный ключ от дубликатов.
7. Использовать `scripts/catalog.py add --root <repo> --game <json> --image <owner-cover>`, `scripts/catalog.py verify --root <repo> --game <json>` при доступном локальном checkout. Скрипт не пушит. Если checkout недоступен — делать те же минимальные изменения через GitHub API с атомарным деревом/коммитом на отдельной ветке и доступными GitHub инструментами. Не предполагать, что файл примера `examples/game.json` содержит настоящий релиз.

### 2. Публикация: довести до доступного разрешённого результата

1. Перед записью проверить права и актуальные ограничения репозитория. При разрешении — создать ветку с текущего main, записать **только** целевые страницы, инвентарь, постер и sitemap, открыть PR и провести проверки без ослабления охранников. Не оставлять PR как «опубликовано». Если GitHub workflow/автоматика может законно завершить merge — использовать её, но не включать auto-merge вопреки правилам.
2. Если разрешён только MGL — подготовить полный минимальный PR/патч в MGL; выяснить существующий разрешённый механизм продвижения в MG и использовать его по возможности **без просьбы пользователю повторять данные**. Если такого механизма в доступных инструментах нет, кратко назвать конкретный оставшийся блокер. Не выдавать прямой доступ GitHub за разрешение нарушать правила.
3. После разрешённого merge/пуша читать `main` SHA и workflow `Publish complete META6 site`, статус `success` + шаг `Confirm live games, SEO catalog and sitemap revision`, где actual `curl -fsSL` с query `?rev=SHA` и `cmp` с build `_site` подтверждают свежесть контента. Если подтверждения нет, самостоятельно проверить HTTP live. Избегать ложных успехов: **успех workflow без live-content проверки недостаточен**.
4. Проверить на живом сайте все 8 страниц, что новая карточка первая, её обложка отвечает 200 и действительно изображение, обе текстовые и графическая ссылки ведут точно в Playgama; JSON-LD и количество карточек согласованы, `sitemap.xml` отвечает 200. Отдельно проверить mobile view/клик через браузер, когда доступен. Если live не обновился — не делать повторный add; чинить deploy/cache или фиксировать точный блокер.
5. После успешного выполнения дать **одну кликабельную ссылку на каталог**. Если пользователь спрашивает о проблеме — кратко назвать факт. Если работа не завершена — не использовать «опубликовано» и не делать фиктивную ссылку на результат; дать точный статус и единственный ближайший блокер.

## Дополнительные ловушки, устраняющие ошибку 23.11.2026

- Ловушка A: если `main` уже содержит `https://playgama.ai/play/l6qm5mss7ch6pu`, 18 карточек, а workflow `Publish complete META6 site` на этом SHA успешен с `curl`+`cmp`, **не говорить «не вижу игру / ещё не опубликована»**. Сначала открыть live; если live недоступен, так и указать.
- Ловушка B: не полагаться на `games` (14 подтверждённых) как полный список — `pendingGames` (в том числе новые из каталога) и реальные карточки могут увеличить текущий total. Считать живые карточки, а не `games.length`.
- Ловушка C: URL в инвентаре ≠ HTML карточка; HTML в GitHub main ≠ опубликованный HTML; успешный upload Pages ≠ обложка видна. Проверять каждую границу отдельно.
- Ловушка D: первый `add` не должен трогать прежние игры; повторный `add` должен перейти в `verify`/repair, а не создать вторую карточку. Перестановка уже существующего URL требует уточнить намерение только если это действительно существенно.
- Ловушка E: ошибки сетевого доступа у проверяющего агента не равны 404 у пользователя; использовать независимые источники/логи, не придумывать результат проверки.
